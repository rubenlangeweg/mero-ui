# Responsive layouts and documentation for Mero UI

On a first visit, Studio opens tasks in List when the workspace has 33rem of usable width or less. An explicit view in the URL takes priority, followed by the user's last choice for that screen. Bookings opens in Week on a first visit. [Responsive layout guide](http://127.0.0.1:4173/docs/responsive-layouts)

The mobile regression opens a company, marks a task Done and goes Back to the same task link. The company’s open count updates. In phone emulation, Agenda showed the next appointment and Week showed an available 90-minute slot that the demo server accepted. Physical iOS Safari and Android Chrome testing remains open. [Company task regression](../../test/studio-mobile-journey.test.mjs)

## Baseline before the pilot

Measured on 20 November 2026 with seeded Studio data in Chromium. The phone viewport was 390 × 844 CSS px with touch emulation. The desktop viewport was 1280 × 900. A third pass constrained the app to 390 px inside that desktop viewport. These measurements describe layout. Physical phone, software keyboard and screen reader checks remain open. [Existing review coverage](../component-standards.md)

| Screen | 390 px phone | 1280 px desktop | Product decision |
| --- | --- | --- | --- |
| Task board | One lane per row. The first started 300 px from the page top and Done started at 1,241 px. List is available. | Four lanes side by side. | Try List first for finding and updating a task. Keep Board one tap away for comparing stages. [Task board](http://127.0.0.1:4173/layouts/dashboard?view=board) |
| Bookings | Week shows a 672 px grid in a 361 px scroll area. The page itself fits. | The entire week fits in its 1,020 px area. | Try Agenda first for locating an appointment. Test Week separately for finding an open room and time slot. [Bookings](http://127.0.0.1:4173/layouts/dashboard?view=calendar) |
| Companies | Opening a company replaces the directory with its record. | Directory and record sit side by side. | Use this as the first documented list/detail pattern. Show selection, Back and a direct record link at both widths. [Companies](http://127.0.0.1:4173/layouts/dashboard?view=companies) |

All three screens also adopted their narrow layout inside the 390 px desktop container. In touch emulation a Studio navigation link measured 44 px high, the Board switch 29 px, and a lane’s add button about 25 px square. Prioritize the frequently tapped actions. ## What the references support

| Reference | What it documents | What to take into Mero |
| --- | --- | --- |
| IBM Carbon and MUI | Carbon scales its grid from 4 to 8 to 16 columns. MUI uses a default of 12 and supports responsive spans. [Carbon 2x Grid](https://www.carbondesignsystem.com/building-blocks/foundations/2x-grid/overview) · [MUI Grid](https://mui.com/material-ui/react-grid/) | Agree on shared edges, gutters and spacing first. A weekly calendar, a four-stage board and a company record each have a natural structure. A mandatory column count adds little to these examples. |
| Tailwind and Android adaptive layouts | Tailwind demonstrates components responding to their parent’s width. Android documents how a selected item moves between single and dual panes as the available space changes. [Tailwind container queries](https://tailwindcss.com/docs/responsive-design#container-queries) · [Android list/detail](https://developer.android.com/develop/ui/compose/layouts/adaptive/canonical-layouts#list-detail) | Size reusable patterns against their host. Document which item stays selected when a second pane appears and where Back takes the user. |
| Linear and FullCalendar | Linear offers Board and List over the same records and documents view preferences. FullCalendar offers a chronological list and a time grid, with a configurable initial view. [Linear boards](https://linear.app/docs/board-layout) · [Linear display options](https://linear.app/docs/display-options) · [FullCalendar List](https://fullcalendar.io/docs/list-view) · [TimeGrid](https://fullcalendar.io/docs/timegrid-view) | List-first and Agenda-first are Mero proposals. A list answers “what’s next?” well. A time grid exposes gaps that matter when scheduling. Test both tasks before adopting a default. |
| Atlassian and Adobe | Atlassian documents an alternative action for dragging, move announcements and focus restoration. Adobe describes mobile autocomplete obscured by the iOS keyboard during device testing. [Atlassian drag accessibility](https://atlassian.design/components/pragmatic-drag-and-drop/accessibility-guidelines/) · [Adobe combobox research](https://react-aria.adobe.com/blog/building-a-combobox) | Exercise the status control with a thumb and keyboard. Test a booking correction on a physical phone with the keyboard open before claiming mobile support for that flow. |
| HeroUI, Radix and daisyUI | HeroUI groups examples around real control states. Radix describes key presses and focus destinations. daisyUI pairs rendered controls with short class references and HTML. [HeroUI Select](https://heroui.com/en/docs/react/components/select) · [Radix Select keyboard behavior](https://www.radix-ui.com/primitives/docs/components/select#keyboard-interactions) · [daisyUI Select](https://daisyui.com/components/select/) | Put the smallest copyable example first. Include the meaningful states, keys, touch actions and focus destinations for that specific control. |
| HeroUI Pro, shadcn/ui and GOV.UK | HeroUI Pro organizes layouts as working applications. shadcn shows the preview and files that make up a block. GOV.UK documents the full journey for changing an answer and returning with the value retained. [HeroUI Pro templates](https://heroui.pro/docs/react/templates) · [shadcn sidebar blocks](https://ui.shadcn.com/blocks/sidebar) · [GOV.UK change an answer](https://design-system.service.gov.uk/patterns/check-answers/#let-users-go-back-and-change-their-answers) | Give each layout a task, a standalone link, its constituent components and the specific handler. Demonstrate how the user gets back to their work. |

## How to document it

| Where | What the reader needs | First example |
| --- | --- | --- |
| **Docs → Layout and responsiveness**, beside Design principles | Show a stack, wrapping row, card grid and list/detail composition. Label the host width. Let readers narrow a preview inside a wide page and copy the same HTML. Explain when items wrap, which parts can scroll and which gaps are shared. | Use the existing `.mero-row`, `.mero-stack` and metrics styles. The Stack catalog entry is an overlapping media deck. Mark the Studio company layout as an application recipe. Promote a reusable class when a second layout needs the same behavior. [Core styles](../../ui/mero.css) · [Layout styles](../../ui/mero-layouts.css) |
| **Component catalog** | Say when to use the control. Show its HTML and required assets, meaningful states, narrow behavior, keyboard and touch interaction, and who owns the value. For a server interaction, show the submitted fields, swap target, error and focus after completion. | Start with Cell Switch and Kanban. Add optional guidance to their existing catalog entries so the page and the example stay together. Other components can omit sections that do not apply. [Catalog page renderer](../../site/catalog-pages.mjs) |
| **Layouts → Studio workbench**, alongside Preview, Template and HTTP exchange | Describe one task, how the desktop and compact views differ, what survives Back, and how to run or adapt the example. Link to the screen renderer and mutation handler. Keep the copyable template tied to the visible screen. | For the task board, link to the company-filtered List and its handler. For Bookings, show completing a booking and correcting a room conflict. Keep this guidance in the public workbench, outside Studio’s product navigation. [Layout workbench](../../site/layout-workbench.mjs) |

**Worked component example.** The catalog Kanban lets a user drag a card or choose its destination using **Move to**. Either action updates the current document and emits the bubbling event `mero:kanban-move` with `card`, `from` and `to`. A developer who needs the change to survive reload must connect persistence. Link directly to the Studio implementation as the server-backed example. [Catalog Kanban](http://127.0.0.1:4173/components/kanban) · [Event implementation](../../ui/mero-collections.js)

**Worked layout example.** Open Forma Works, choose a task, change its status and return to the company. In Studio, both task presentations use the same record. The form posts `operation=move`, the task ID and the new status to `/demo/studio/tasks`. A successful HTMX submission replaces `#studio-workspace`. Invalid input returns HTTP 422. A successful native submission redirects with HTTP 303. Show the company’s updated open-task count when the task moves to Done. Studio holds demo records in memory until its server restarts. [Try Forma Works](http://127.0.0.1:4173/layouts/dashboard?view=companies&company=forma) · [Board handler](../../site/studio-board.mjs) · [HTTP regression](../../test/studio-workflows.test.mjs)

## Pilot delivery plan

| Owner | Deliverable | Acceptance |
| --- | --- | --- |
| Layout foundations | Inventory the gaps in Studio’s existing CSS. Name shared panel padding, section spacing and grid gaps where the measurements serve the same purpose. Publish examples with inline-size controls. | Put the same markup in a full desktop page and a narrow panel. Headers, fields and panels align. At 320 CSS px the page reflows. Where a two-dimensional view needs horizontal scrolling, confine it to the view. [WCAG reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html) |
| Mobile workflows | Give Board, List, Week and Agenda explicit URL values. Pilot an explicit URL choice first, a saved preference for that screen second, and a width-based default for an unchosen view. At baseline, selecting Board or Week cleared `display`, so the app could not distinguish an explicit choice from a first visit. | A phone user can choose Week, open a booking, correct it, refresh and go Back without switching to Agenda. A shared link wins over local preference. Resizing keeps the selected record and draft. Serve a usable initial HTML view when width is unknown or JavaScript is off. [Board renderer](../../site/studio-board.mjs) · [Calendar renderer](../../site/studio-bookings.mjs) · [HTMX history](https://htmx.org/attributes/hx-push-url/) |
| Documentation | Publish the foundation guide, extend two existing component entries and add screen-specific guidance for Board, Bookings and Companies. Generate examples from the existing registry and workbench. | A developer can copy a control into a blank page, identify who saves its value and find the handler for the full workflow. Have someone unfamiliar with Mero try this before extending the format to the full catalog. [Component standards](../component-standards.md) |
| Verification | Extend the existing audit with explicit List, Agenda, selected record and correction states. Test a narrow desktop container, phone and tablet widths, touch, keyboard, enlarged text, RTL and browser history. Record physical iOS Safari and Android Chrome results separately. | Complete a task move without dragging. On a phone, both locate an appointment and find a free 90-minute room slot. With the keyboard open, trigger and correct a booking conflict. Verify focus and return position. Aim for 44 × 44 CSS px for frequent touch actions. WCAG 2.2 AA sets a 24 × 24 CSS px minimum with exceptions. [Catalog audit](../../scripts/audit-catalog.mjs) · [WCAG target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) · [WCAG dragging](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html) |

Foundations, docs structure and test fixtures can start in parallel. Agree on the URL and preference behavior before changing defaults. Publish the compact-view recommendation after the phone workflows have been tried.
